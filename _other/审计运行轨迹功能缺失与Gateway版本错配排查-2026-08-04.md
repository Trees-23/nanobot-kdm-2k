# 审计运行轨迹功能缺失与 Gateway 版本错配排查

日期：2026-08-04
范围：聊天页子 Agent 状态、工具恢复关系、子 Agent 结果回传、真实 Gateway 部署一致性

## 现象

最近两轮真实聊天验收出现以下问题：

1. 聊天框看不到子 Agent 状态。
2. 工具恢复链路默认隐藏，只能点击节点或关系后查看。
3. 三个子 Agent 运行时，只看到一条结果回传到主 Agent。
4. 工具恢复测试看不到恢复链路。

这些现象不是一个问题，分别涉及部署版本、审计数据证据、前端默认可见性和测试提示词是否真的触发失败工具调用。

## 只读证据

### 当前 8765 不是当前分支的 Gateway

| 项目 | 实际值 |
| --- | --- |
| 容器 | `nanobot-gateway-v2` |
| 镜像 | `nanobot-tool-error-recovery:8056ec1d-r3` |
| 镜像标注分支 | `codex/tool-error-recovery-plan` |
| 镜像标注提交 | `8056ec1d2ab6427390c469bf8a0840efcedcb2a8` |
| 当前代码分支 | `codex/subagent-state-plan-v2` |
| 当前代码 HEAD | `0a8a989d` |
| 容器挂载 | `runtime/v2-exam-20260802-145531 -> /home/nanobot/.nanobot` |

当前分支存在 `nanobot/webui/subagent_api.py`，运行容器中不存在该文件。实际接口状态如下：

```text
GET /api/subagents/tasks -> 404
GET /api/audit/traces   -> 200
```

前端只有收到 `subagent_snapshot` 或 `subagent_status_changed` 才会设置子 Agent 状态。因此聊天框没有子 Agent 状态，首先是 Gateway 没有提供当前协议，而不是状态条组件单独失效。

### 三个子 Agent 的运行数据存在，但回传边不完整

本轮实际图数据包含：

| 图元素 | 数量 |
| --- | ---: |
| `spawn_branch` | 3 |
| `delivery` 节点 | 3 |
| `result_return` 边 | 1 |

三个子运行和三个交付结果没有全部消失；旧 Gateway 的图投影只绑定了一条结果回传边。本轮事件没有 `subagent_task_id`、`subagent_result_delivered` 或 `input_injected(injection_source=subagent_result)` 结构化证据，只能退回旧的相邻事件推断，最终只得到一条边。

### 本轮工具恢复测试没有产生失败事件

三份运行中共记录 23 次工具调用，全部为成功：

```text
tool_finished.status = ok
recovery_of_tool_call_ids = []
tool_recovery = 0
```

因此本轮没有可以绘制的工具恢复关系。仅仅让模型“之后读取另一个文件”也不保证被审计识别为恢复：恢复边要求同一运行中的失败工具调用，随后出现相同重试或可验证的资源路径纠正。

### 次级关系默认隐藏是当前 UI 的明确策略

当前 `TraceGraph.tsx` 默认只显示结构关系；`result_return`、`tool_recovery`、`task_recovery` 等关系需要选中节点、点击关系按钮或进入结果/恢复焦点模式后显示。

组件还使用单个 `activeRelationId` 保存主动展开的关系，所以交互上一次只会突出一条关系。这是当前视觉重构的设计结果，不是后端数据丢失。

## 结论

```text
当前分支源码
    ↓（没有重新构建/替换 Gateway）
旧分支 Docker Gateway
    ↓（缺少子 Agent 协议和结构化任务证据）
新前端只能看到部分旧审计图
    ↓
次级关系默认隐藏 + 旧兼容推断只连出一条回传边
```

工具恢复测试还叠加了独立问题：提示词没有确保真的先执行失败工具调用，因此没有恢复证据。

### 提示词必须以 Agent 实际 workspace 为准

工具路径不是宿主机仓库路径。当前 Gateway 的配置将宿主机目录：

```text
runtime/v2-exam-20260802-145531
    -> /home/nanobot/.nanobot
```

而 Agent 实际使用的 workspace 是：

```text
/home/nanobot/.nanobot/workspace
```

因此宿主机上的：

```text
runtime/v2-exam-20260802-145531/workspace/prompts/README.md
```

对 Agent 的 `read_file` 应写成相对 workspace 的：

```text
prompts/README.md
```

不能直接使用宿主仓库根目录的 `README.md`，也不能把 `/home/kdm/...` 等宿主绝对路径直接交给 Agent。主 Agent 或子 Agent 如果配置了独立 workspace，也必须先读取其实际 workspace 再选择测试文件。

后续所有工具恢复提示词的编写门禁：

1. 先确认运行中容器的配置、挂载目录和 Agent workspace。
2. 在该 workspace 中确认纠正后的目标文件真实存在。
3. 使用相对 workspace 的路径构造“错误路径 -> 正确路径”恢复对，并确保错误路径只多出一层不存在的目录。

## 是否只重启 Gateway

不是。只重启现有容器只会再次启动旧镜像，问题不会改变。

正确顺序是：

1. 确认当前分支和 HEAD 是要验收的版本。
2. 使用当前分支重新构建 Gateway 镜像；代码、审计 schema 或 WebUI 改动较多时使用 `--no-cache` 消除旧层污染。
3. 如果审计 schema/index 也发生变化，同时重建 `nanobot-cli` 镜像。
4. 保留当前 runtime 挂载目录，停止旧 Gateway，使用同一配置和同一 runtime 挂载强制重建容器。
5. 仅在 schema/index 变更或状态明确要求时重建审计索引。
6. 真实浏览器验证容器源码、容器内 bundle、实际 `8765` bundle 是同一构建闭包。

仓库默认 Compose 的基本操作顺序：

```bash
# 在仓库根目录，先确认分支、HEAD 和受保护改动
git status --short --branch
git rev-parse HEAD

# 使用当前分支构建；为排除旧镜像层，可使用 --no-cache
docker compose build --no-cache nanobot-gateway
docker compose --profile cli build --no-cache nanobot-cli

# 仅在确认 Compose 项目、容器名和 runtime 挂载与现有部署一致后执行
docker compose stop nanobot-gateway
docker compose up -d --force-recreate nanobot-gateway

# 部署后的最低检查
docker compose ps
curl -fsS http://127.0.0.1:18790/health
docker compose logs --since=5m nanobot-gateway
```

禁止执行 `docker compose down -v`。

当前实际容器名是 `nanobot-gateway-v2`，挂载的是 `runtime/v2-exam-20260802-145531`，并非默认 Compose 输出的 `nanobot-gateway` / `./runtime` 组合。因此执行前必须确认实际使用的 Compose 文件、项目目录和 runtime 路径；不能盲目执行根目录命令，以免启动另一套 Gateway 或挂载错数据。

重建后必须额外验证：

```text
GET /api/subagents/tasks       不得返回 404
真实聊天收到 subagent_snapshot 或 subagent_status_changed
三个子 Agent 对应三个 delivery 和三个 result_return
失败工具事件带 recovery_of_tool_call_ids
真实 8765 页面加载的是本次镜像内 bundle
```

## 防止再次发生的部署门禁

每次验收前固定记录以下信息：

- Git 分支和 HEAD。
- Docker 容器 ID、镜像 tag/digest、镜像构建提交标记。
- 容器内 `nanobot/webui/subagent_api.py` 是否存在。
- 容器解析出的 workspace 和 audit root。
- 宿主 dist、容器 dist、实际 `8765` 返回的 index/bundle SHA-256。
- `/api/subagents/tasks`、`/api/audit/traces` 的鉴权后状态码。
- 真实浏览器控制台、WebSocket、页面错误和审计图摘要。

任何一项不一致，都先判为部署不一致，不把结果归因于前端视觉逻辑。

## 场景提示词

下面提示词只读，不创建、修改或删除文件。必须在重新部署当前分支 Gateway 后使用。

### 场景 A：工具恢复

```text
请执行一次“工具失败与资源路径纠正恢复”审计演示。必须使用工具，不能只用文字模拟；全程只读，不得写入、修改或删除文件。

1. 先调用 create_goal，目标为：完成一次可验证的 read_file 失败，并在同一运行中完成资源路径纠正后的成功读取。
2. 在继续任何其他工具调用前，必须先调用：
   read_file(path="__audit_missing__/prompts/README.md")
   这个路径是故意多出一层不存在的目录，必须让该工具真实返回失败。
3. 确认工具返回失败后，调用：
   read_file(path="prompts/README.md")
   这是当前 Agent workspace 中确实存在的目标文件，必须等待成功结果。
4. 最终报告第一次工具的失败、第二次工具的成功，并调用 update_goal 标记完成。

如果第一步没有产生真实 tool_finished error，就停止并报告“恢复场景未生成失败证据”，不要伪造恢复成功。
```

### 场景 B：三个子 Agent，各自带工具恢复

```text
请执行一次“三子 Agent 并行 + 每个子 Agent 工具恢复”的审计演示。必须真实调用工具，不得只输出计划；全程只读，不得写入、修改或删除文件。

1. 先调用 create_goal，目标为：三个 required 子 Agent 各完成一次 read_file 路径纠正恢复，主 Agent 等待并汇总全部结果。
2. 连续调用三次 spawn，全部设置：
   required=true
   task_group="three-agent-tool-recovery-20260804"
   分别使用 label：检查工作区、检查 Python 测试、检查 WebUI 测试。
3. 三个子 Agent 的任务内容必须分别是：
   - 先调用 read_file(path="__audit_missing__/prompts/README.md")，确认真实失败；
   - 随后调用 read_file(path="prompts/README.md")，确认路径纠正后的成功读取；
   - 返回失败摘要、成功摘要和恢复结论；不得调用写入类工具。
4. 三次 spawn 成功后，主 Agent 只调用一次 await_subagents(task_group="three-agent-tool-recovery-20260804")，等待三个任务全部进入终态。
5. 汇总三个子 Agent 的结果，并调用 update_goal 标记完成。

验收要求：三个子 Agent 都必须出现独立的失败工具事件、成功纠正事件和恢复关系；如果任一子 Agent 没有失败事件或没有成功纠正事件，必须如实报告失败，不要把普通成功任务算作恢复。
```
