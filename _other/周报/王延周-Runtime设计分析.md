# 王延周 Runtime 设计分析与可借鉴点

## 结论

从周报看，王延周并非只是在做“运行一个 Agent”的循环，而是在建设一套 **可持久化、可干预、可恢复、可观测、可扩展的任务运行平台**。其最值得借鉴的不是某个具体语言或框架，而是把 Agent 执行拆为清晰的领域对象和生命周期，并让控制台、事件、工具、沙箱都围绕该生命周期协作。

## 一、设计脉络

```text
配置中心
  ↓
实例管理（创建 / 启动 / 持久化 / 恢复 / 模型 SDK）
  ↓  1:1 绑定
任务系统（状态机、日志、干预、队列、重试）
  ↓
事件总线 / 完整追踪链路
  ├─ 控制台：实时状态、工具审批、会话回放、工作流图
  ├─ 工作区与沙箱：隔离执行、插件快照、资源回收
  └─ Hook / 插件 / Skill / tool-cli：扩展执行能力
```

这条主线在周报中连续出现：早期先做 `trace_id`、任务取消与公平并发；中期形成 Go Runtime 的配置、实例、任务、事件分层；后期把插件、工具协议、外部接入和交付物生命周期接入这个执行模型。

## 二、最值得学习的设计

### 1. 以“实例—任务”而非“聊天窗口”作为运行时核心

周报中任务绑定单一智能体实例，实例负责创建、启动、持久化、恢复和 SDK 选择，任务负责状态、日志和用户操作。这比直接把聊天会话当执行单元更稳健：

- 会话可以中断、重启后恢复，任务记录独立归档；
- 切换模型时可启动新实例继续任务，而非在同一个不透明上下文中热切换；
- 任务日志按任务隔离，控制台可准确呈现任务而不是混杂的全局日志；
- 实例、任务、工作区、会话可分别建模并形成明确关联。

对本仓库的启示：`Session` 仍应侧重对话历史，长期执行需要独立的 `TaskRun` / `AgentInstance` 语义。不要仅靠 session history 推断任务是否仍在运行、能否恢复或由谁执行。

### 2. 生命周期需要“可恢复”而不只是“可取消”

暂停、重启、中止、跳过、队列串行激活、主实例切换、心跳和静止检测共同构成了长任务恢复能力。特别值得注意的是工作区回收事故后的修正：由物理删除改为**非破坏性停容器保记录**，404 时重建，并补漏孤儿容器。

可迁移原则：

- 将资源清理分为“停止执行、保留记录、延迟删除”三个动作；
- 恢复路径必须可重复执行（例如资源不存在时重建，而不是直接失败）；
- 记录状态与外部资源状态可能漂移，需有孤儿扫描和对账；
- 把“暂停/恢复”的语义和状态转换写成显式状态机，并为每个转换记录原因、操作者和 trace。

### 3. 事件是控制面和数据面的共同语言

从 `trace_id`、事件总线、完整追踪链路，到工具审批和执行结果回传，报告反映出一个正确方向：前端状态不是靠轮询拼出来的，而是消费同一条带关联 ID 的事件流。

建议借鉴的事件最小字段：

| 字段 | 用途 |
| --- | --- |
| `trace_id` / `task_id` / `instance_id` | 串起一次任务、一次实例和其子事件 |
| `sequence`、时间戳 | 处理乱序、回放和断线补偿 |
| `type`、`payload_version` | 演进协议且避免前端猜数据形态 |
| `actor`、`source` | 区分用户、主 Agent、子 Agent、系统和工具 |
| `status`、`reason` | 支撑取消、失败、恢复和审计 |

本仓库已有消息总线、Agent Loop、Runner 和 WebUI 轨迹能力，宜先补齐这些对象间的关联与状态语义，再扩展 UI。不要在前端额外发明一套与运行时不同的状态机。

### 4. 沙箱、工作区和插件都是受管资源

周报中的 Docker 沙箱、工作区准备/收尾 Agent、插件目录快照挂载、工作区级插件隔离、SSH 注入及回收，说明运行时不能把文件系统当作无状态临时目录。它们需要明确的所有权、创建、挂载、停止、回收和审计。

可学习的实践：

- 工作区初始化与收尾做成独立、可观察的步骤；
- 以项目/任务定义隔离边界，并在资源记录中保存外部资源标识；
- 配置及密钥区分公共配置、用户私有配置和短期临时凭据；
- 回收默认可逆，删除需要明确的保留期和审计。

### 5. 扩展能力要“协议统一 + 按需发现”

其工具管理使用标准工具协议、`tool-cli`、MCP 接入和用户颗粒度配置，并通过工具组和 `describe` 实现渐进加载。这解决两类常见问题：全部工具塞入上下文造成 token/选择压力，以及各供应商 SDK 事件形态不同使上层复杂化。

建议：统一工具调用、结果、审批和错误的内部事件模型；把工具目录、权限、参数模式和帮助信息作为可查询元数据。只有任务需要时，才向模型展开具体方法和详细参数。

### 6. 人机协同必须是运行时的一等能力

交互式/自动任务分流、运行中插入消息、工具审批、AskUserQuestion 回传，避免把“等待用户”伪装成模型或工具超时。对长任务而言，用户输入是一个可持久化、可追踪、可恢复的事件，而非阻塞协程中的临时 `input()`。

## 三、建议落到 nanobot 的优先级

| 优先级 | 建议 | 目标 |
| --- | --- | --- |
| P0 | 明确 `Session`、`TaskRun`、`AgentInstance`、`Workspace` 的责任和关联；补充任务状态机 | 让中断、恢复、取消和审计有稳定语义 |
| P0 | 为消息、工具、子 Agent、状态变更统一关联 ID 和事件 schema | 把现有轨迹与真实运行对象对齐 |
| P1 | 抽出可逆的工作区/资源生命周期与对账机制 | 降低回收事故和资源泄漏风险 |
| P1 | 把等待用户、审批、恢复做成持久化任务事件 | 支持长任务安全地暂停和继续 |
| P2 | 建立 Hook/插件生命周期与工具渐进加载 | 扩展能力而不把核心 Loop 变成条件分支集合 |
| P2 | 归一化不同 provider/CLI 的工具事件 | 减少 WebUI 和 Runner 的供应商特判 |

## 四、不能直接照搬的部分

- 周报描述的是 Go Runtime 和 AI 员工平台；本仓库是 Python `AgentLoop` / `AgentRunner` 架构。应迁移领域模型和边界，不应为了形式一致重写语言或替换现有消息总线。
- 心跳、主编排器、工作区准备 Agent 会引入额外模型调用和状态面。小任务应保持轻量路径，只有长任务或复杂协作才启用。
- “自动回收”“自动重建”必须受到工作区保护、资源所有权和用户确认策略约束，不能对长期 workspace 进行隐式破坏性操作。
- 周报中的完成度、稳定性与效率数字均为自述，适合作为设计线索，不可直接当作容量或 SLA 依据。
