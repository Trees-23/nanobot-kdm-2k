# 审计运行轨迹复现提示词

## 使用前提

该提示词必须发送给已经重启到本次改造版本 gateway 的 nanobot。请新建会话，避免旧 Run
和历史 Audit 干扰判断。不要在生产配置目录制造缺失文件，所有读取都限定在仓库的评测 fixture。

## 可直接发送的提示词

```text
这是一次审计运行轨迹黑盒评测。请严格按顺序执行下面的 Tool 调用，不要合并步骤，不要因为某一步失败而停止，也不要自行改写路径。

1. 使用 read_file 读取：
   _other/评测/fixtures/recovery-target/runtime/config.json
   这个路径预期不存在。记录失败后继续。

2. 使用 read_file 读取：
   _other/评测/fixtures/unrelated/config.json
   它与第一步 basename 相同，但属于不同逻辑资源。成功后继续。

3. 使用 read_file 读取：
   _other/评测/fixtures/recovery-target/config.json
   它是第一步的确定性纠错路径。成功后继续。

4. 使用 spawn 创建一个 label 为 audit-child-check 的子任务。子任务只做以下事情：读取
   _other/评测/fixtures/child/context.txt，并在最终回答中原样返回其中的 marker。不要让子任务修改任何文件。

5. 如果当前会话提供等待子任务的能力，则等待 audit-child-check 完成并接收结果；否则继续执行下一步，让子任务在后台完成。

6. 使用 web_search 搜索：nanobot audit trace deterministic evaluation
   无论成功、普通失败还是 timeout 都继续。不要重复搜索来人为制造恢复判断。

7. 最终只输出以下执行摘要：三个 read_file 调用是否成功、child marker、web_search 状态。不要读取或修改 Audit JSONL，也不要声称自己验证了 Graph UI。
```

## 预期触发的能力

[] a. 第一步稳定触发 `FileNotFoundError/file_not_found` 和安全错误摘要。

[] b. 第二步验证“同 basename、同 Tool 不足以判定恢复”。

[] c. 第三步触发显式 `recovery_of_tool_call_ids`。

[] d. 多次 Tool 调用形成 `sequence` 执行上下文。

[] e. `spawn` 形成 main/child `spawn_branch`，child 完成后形成 `result_return`。

[] f. `web_search` 产生正常或异常搜索节点；真实 timeout 不稳定，必须另跑试卷第七题的故障注入测试。

## 复现后的 UI 检查顺序

[] a. 在运行轨迹列表打开刚产生的最新 Trace。

[] b. 选择第一个失败的 `read_file`，检查根因、影响、恢复和原始事件。

[] c. 对该节点依次点击“因果链”和“执行上下文”，记录命中节点/边数量。

[] d. 选择 main Run、`spawn` 或 child Run，检查“结构分支”。

[] e. 选择 child 返回相关节点，检查“恢复链路”；无证据时应明确显示零命中。

[] f. 从原始事件定位 `ToolFinished`，再显式打开 Payload。

[] g. 使用“定位 main Run”“定位首个异常”和“图例”，验证反馈与键盘操作。
