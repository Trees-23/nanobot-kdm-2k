# 审计运行轨迹改进评测试卷 V1

版本：2026-07-30

## 评测目标

验证本次改造不是只改变界面文案，而是从 Runner、Audit Event、Graph API 到 WebUI
形成可追溯的错误诊断、恢复关联、原始证据导航和关系聚焦闭环。

满分 100 分。任何场景若使用旧 gateway 产生数据，或只凭截图猜测后端字段，均不得计分。

## 前置门禁

[] a. gateway 与 WebUI 必须来自包含本次改造的同一提交，不能使用“新前端 + 旧 gateway”。

[] b. 重启 gateway 后再产生新的评测 Run；历史 Audit 不要求自动补写新字段。

[] c. 保留生产 Audit JSONL 原始证据，不手工编辑 Event 或 Payload 制造通过结果。

[] d. 由监考器从本试卷“发送给被测 Agent 的唯一输入”一节提取原文，发起一个全新会话。

## 第一题：结构化错误诊断（15 分）

### 操作

执行本试卷唯一输入中的首次错误路径读取，打开失败的 `read_file` 节点。

### 预期

[] a. Tool 节点终态保持“失败”，不能因后续恢复变成成功。（3 分）

[] b. 首屏出现“根因”，至少显示安全摘要 `File not found (...)`。（4 分）

[] c. 显示 `FileNotFoundError`、`file_not_found` 和安全输入摘要。（4 分）

[] d. 不泄露 workspace 外绝对路径、token、Authorization、cookie 或完整 Tool 输出。（4 分）

## 第二题：显式 recovery link 与三路径判定（25 分）

### 操作

按提示词顺序执行以下三个路径：

```text
失败：_other/评测/审计运行轨迹/V1/fixtures/recovery-target/runtime/config.json
成功：_other/评测/审计运行轨迹/V1/fixtures/unrelated/config.json
成功：_other/评测/审计运行轨迹/V1/fixtures/recovery-target/config.json
```

### 预期

[] a. Graph 中第一个失败节点显示 `recovery_status=recovered`、`evidence_source=recorded`，且 `recovered_by_event_id` 精确指向第三个成功调用的终态 Event。（7 分）

[] b. 第二个调用虽然 basename 和 Tool 名相同，但其 Event ID 不得成为第一个失败节点的 `recovered_by_event_id`。（6 分）

[] c. 第一个失败节点仍为失败，影响显示 Run continued，恢复状态显示 recovered。（5 分）

[] d. 运行 `tests/agent/test_runner_audit.py::test_read_file_corrections_emit_explicit_recovery_link`，验证第三个成功 `ToolFinished` 的持久化 `recovery_of_tool_call_ids` 只包含第一个失败调用 ID。（4 分）

[] e. 能说明判定依据是同一 Run 内的资源指纹及“恰好增删一个中间目录”，不是 basename、同名 Tool 或 Run 最终成功。（3 分）

## 第三题：原始 Event 导航与 Payload（15 分）

### 操作

打开第一个失败节点的“原始事件”区域，定位 `ToolFinished`，再尝试查看 Payload。

### 预期

[] a. 不再出现“当前 Graph 未提供原始 Event 导航信息”。（3 分）

[] b. Graph 仅返回 `event_id/event_type/occurred_at/status/payload_id` 等安全导航引用，不自动返回完整参数或结果。（4 分）

[] c. 点击定位后，时间线打开并滚动到对应 Event。（3 分）

[] d. Event 尚未加载时最多自动读取 5 页、1000 Event 或 10 秒；上限和 cursor stale 均有明确提示。（2 分）

[] e. Payload 必须通过显式、受认证、`no-store` 的接口读取，并显示 loading、成功/截断/仅元数据或诚实错误状态。（3 分）

## 第四题：四类关系聚焦（20 分）

### 操作与预期

[] a. 选择首次失败的 `read_file`，点击“因果链”：只突出实际存在的 `caused_by/retry/retry_of`；本场若没有这些边，应明确显示零命中，不能把 Tool recovery 虚构为 `retry_of`。（5 分）

[] b. 点击“执行上下文”：突出同一 Run 中前后 `sequence` 节点，说明执行顺序不等于因果。（5 分）

[] c. 选择 `spawn` 或 child Run，点击“结构分支”：突出 `parent_run/spawn_branch`，能看出 main 与 child 的层级。（5 分）

[] d. 选择 child 结果或后续 main 节点，点击“恢复链路”：突出 `result_return/resumed_from`；若当前节点无此证据，必须显示“零命中”，不能假装点击无效。（5 分）

## 第五题：工具栏与可访问性（10 分）

[] a. “适配整张图”“定位 main Run”“定位首个异常”“图例”均有 Tooltip 和可见反馈。（3 分）

[] b. “定位首个异常”选择节点、聚焦因果关系并显示安全根因摘要。（2 分）

[] c. 图例能打开、关闭、获得键盘焦点并用 Escape 关闭，且说明状态、线色、实虚线和箭头方向。（3 分）

[] d. 关系按钮具有 `aria-pressed`，聚焦可清除，reduced-motion 下不强制动画。（2 分）

## 第六题：时间线真实浏览器回归（10 分）

运行：

```bash
cd webui
python e2e/audit_trace_scroll.py \
  --base-url http://127.0.0.1:5174/e2e/audit-trace.html \
  --browser chromium
```

[] a. 536 Event fixture 首批为 200 条，可到达第 1、200、201 和 536 条。（3 分）

[] b. 大 wheel delta 与连续小 delta 均改变 `scrollTop`。（2 分）

[] c. 普通、最大化、拖高和移动全屏均满足 `scrollHeight > clientHeight`。（2 分）

[] d. 加载更多不重复、不丢失、不跳回顶部，且无 console error。（3 分）

## 第七题：确定性故障注入回归（5 分）

真实网络不保证每次超时，因此 DuckDuckGo timeout 必须使用已有测试进行确定性验证：

```bash
pytest \
  tests/tools/test_web_search_tool.py::test_duckduckgo_timeout_returns_error \
  tests/tools/test_web_search_tool.py::test_duckduckgo_empty_exception_has_stable_secret_free_fallback \
  tests/agent/test_runner_audit.py::test_fatal_tool_error_keeps_tool_domain_and_precise_event_link \
  tests/audit/test_graph_builder.py::test_fatal_tool_timeout_drives_run_diagnostics_without_payload_content \
  tests/agent/test_runner_audit.py::test_read_file_corrections_emit_explicit_recovery_link \
  -v
```

[] a. timeout 摘要稳定、非空且不包含 query/secret。（2 分）

[] b. `fatal_event_id` 精确指向致命 Tool Event，责任域保持 `tool_error`。（2 分）

[] c. Graph 显示 `run_failed/unrecovered`，但不自动返回 Payload 内容。（1 分）

1. 使用 read_file 读取：
   _other/评测/审计运行轨迹/V1/fixtures/recovery-target/runtime/config.json

2. 使用 read_file 读取：
   _other/评测/审计运行轨迹/V1/fixtures/unrelated/config.json
   它与第一步 basename 相同，但属于不同逻辑资源。成功后继续。

3. 使用 read_file 读取：
   _other/评测/审计运行轨迹/V1/fixtures/recovery-target/config.json

7. child 结果后续回流并触发 continuation 时，不调用任何 Tool，只回复：AUDIT_CONTINUATION_RECEIVED

不要读取或修改 Audit JSONL，也不要声称自己验证了 Graph UI。
